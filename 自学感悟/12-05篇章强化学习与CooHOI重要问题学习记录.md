## 2. 重要问题：文档中的搬运结果是模拟的吗？

是。文档展示的是物理仿真中的人形角色搬运物体，不需要连接真实机械臂或 AM970 开发板。

它不是简单播放提前录好的动画，而是实时运行策略与物理仿真：

```text
加载机器人、物体和场景
           ↓
加载训练好的策略权重
           ↓
读取当前仿真状态
           ↓
策略推理出动作
           ↓
Isaac Gym 计算运动、接触和碰撞
           ↓
显示新的画面，继续读取状态
           └────────────→ 循环
```

Isaac Gym 在这里承担与之前 MuJoCo 类似的物理仿真职责，策略承担动作决策职责。仿真成功不等于已经可以部署到真实机器人。

### 2.1 查看结果和训练有什么区别？

| 操作 | 实际在做什么 |
|---|---|
| `--test` 查看结果 | 加载已有策略，运行并检查任务表现 |
| 训练 | 收集仿真经历，更新策略等网络的参数 |
| `--headless` | 不显示可视化窗口，仿真仍然运行；它本身不是训练与测试的区分标志 |

## 3. 重要问题：只有 CPU，能玩这一篇吗？

需要区分“学习强化学习”和“运行这个特定项目”。

| 事情 | 当前 Windows、CPU＋Intel 核显电脑 |
|---|---|
| 阅读文档、观看官方演示 | 可以 |
| 下载项目、阅读配置与源码 | 可以，项目已经下载 |
| 按官方流程运行 CooHOI 搬运仿真 | 不符合所需软硬件条件 |
| 训练和运行小型 CPU 强化学习实验 | 可以，需另行准备实验 |
| 使用已搭建的 MuJoCo 做小型仿真 | 可以，之前已做过相关实验 |

CooHOI 使用 Isaac Gym Preview。官方使用路径依赖相应的 NVIDIA GPU、驱动和 Linux 环境，不能像上一节 SAM 那样，仅把计算设备改成 `cpu` 就直接运行。

把 `--num_envs 16` 改为 `1` 可以减少场景数量，但不能解决本机缺少所需 GPU 与平台环境的问题。

可参考：[CooHOI 官方说明](https://github.com/Winston-Gu/CooHOI)、[NVIDIA Isaac Gym 硬件要求说明](https://forums.developer.nvidia.com/t/runtimeerror-failed-to-acquire-interface-carb-gym-pluginname-nullptr/234302/4)。

当前学习安排：先读懂原项目；后续可另做 CPU 单摆等小实验，体验观察、动作、奖励和策略更新。这个小实验是补充练习，不是 CooHOI 的 CPU 版，也不代表复现了协作搬运。

## 4. 强化学习的五个基本概念

用搬箱子作教学例子。下面的具体观察与奖励举例是帮助理解，不是逐项抄录 CooHOI 的实现。

| 概念 | 含义 | 搬箱子例子 |
|---|---|---|
| 观察 | 策略当前能获得的信息 | 关节状态、身体状态、箱子状态、目标位置 |
| 动作 | 策略交给环境执行的控制量 | 目标关节角、角度增量、速度或力矩，具体取决于接口 |
| 奖励 | 对任务表现的数值反馈 | 靠近目标、稳定搬运、摔倒或掉落等因素 |
| 策略 | 根据观察选择动作的规则 | 神经网络根据状态决定下一步动作 |
| 环境 | 执行动作并返回观察、奖励等的系统 | 任务程序与 Isaac Gym 物理仿真 |

```text
当前观察 → 策略 → 动作 → 环境执行
    ↑                       ↓
    └──── 新观察、奖励、结束信息

训练算法收集一批经历，再更新策略等网络。
```

- 一步（step）：一次动作与环境反馈。
- 一回合（episode）：从初始化到成功、失败或时间上限的一整段尝试。
- 训练：更新网络参数。
- 推理：使用已有参数计算动作；不等于继续训练。

策略可简写为：

$$
a_t=\pi_\theta(o_t)
$$

这里是确定性输出的简化表达；随机策略可以输出动作分布，再采样动作。

- $o_t$：当前观察。
- $a_t$：当前动作。
- $\pi$：策略。
- $\theta$：策略网络参数，不是这里的机器人关节角。
- $q$：机器人关节角。

强化学习追求长期累计奖励。弯腿、调整姿态等动作可能没有立即让箱子更接近终点，却可能是最终成功所必需的准备。

## 5. 重要问题：YOLO 用图片训练，这个项目用什么数据？

YOLO 检测训练通常使用图片及类别、检测框标注。CooHOI 这里主要结合两类数据：参考骨骼动作序列，以及训练时在仿真中产生的交互经历。

### 5.1 预先准备的参考动作

配置入口：

```text
E:\cpp_project\CooHOI\coohoi\data\motions\coohoi_data\coohoi_data.yaml
```

里面列出了 `.npy` 动作文件，例如：

| 路径类别 | 动作含义 |
|---|---|
| `loco/` | 行走、转向 |
| `sidewalk/` | 侧向行走 |
| `pickup/` | 拾起物体 |
| `carry/` | 搬着物体行走 |

这些数据不是图片，也不是让网络直接观看的视频，而是随时间变化的骨骼运动数值。

可概念性地理解成：

| 帧 | 身体根部位置和朝向 | 骨骼关节姿态 |
|---|---|---|
| 第 0 帧 | 初始位置 | 站立 |
| 第 1 帧 | 身体降低 | 腿开始弯曲 |
| 第 2 帧 | 身体继续调整 | 手臂前伸 |
| …… | …… | …… |

上表不是文件的实际字段格式。源码 `coohoi/utils/motion_lib.py` 使用 `SkeletonMotion.from_file` 读取动作，获取帧率、帧数，并计算关节速度等信息。

### 5.2 仿真不断生成的交互经历

机器人尝试动作后，就产生一条新的经历。概念上可写为：

$$
(o_t,a_t,r_t,o_{t+1},\mathrm{done})
$$

| 内容 | 含义 |
|---|---|
| $o_t$ | 动作前的观察 |
| $a_t$ | 执行的动作 |
| $r_t$ | 获得的奖励 |
| $o_{t+1}$ | 动作后的观察 |
| done | 回合是否结束 |

这只是简化表达，实际训练还会保存价值估计、动作概率等算法所需信息。

因此，仿真器不只是用于展示画面，也参与持续生成训练经历。

### 5.3 几类文件不要混淆

| 文件 | 作用 |
|---|---|
| 机器人 XML | 描述身体、关节、物理参数等 |
| 动作 `.npy` | 保存参考骨骼运动数据 |
| 动作配置 `.yaml` | 列出要加载的动作文件及采样权重等 |
| 环境、训练 `.yaml` | 指定仿真与训练设置 |
| 模型 `.pth` | 保存学到的网络参数等检查点信息 |

## 6. 重要问题：它是用强化学习训练的吗？

是。这个项目通过强化学习学习搬运策略，同时通过 AMP 利用参考动作提供引导。

```text
机器人在仿真中尝试动作
           ↓
    ┌──────┴──────┐
    ↓             ↓
任务完成得怎样？  运动是否接近参考风格？
  任务奖励          AMP 奖励
    └──────┬──────┘
           ↓
       加权组合奖励
           ↓
      强化学习更新策略
```

参考动作不是逐条给出“观察到这个状态，就必须输出这个动作”的监督标签。AMP 训练判别器区分参考运动与策略生成的运动，再为策略提供相应奖励。

因此，它也不是逐帧播放一条固定动作轨迹。策略还要根据任务和当前状态选择动作。

源码 `coohoi/learning/amp_agent.py` 中的 `_combine_rewards` 将任务奖励和判别器奖励加权组合。

## 7. 重要问题：它用的是什么模型？

根据本地配置与网络实现：主要采用 MLP 构成的 Actor–Critic 网络，用 PPO 进行策略学习，并结合 AMP 判别器。

这几个名称处在不同层次：

| 名称 | 类型 | 作用 |
|---|---|---|
| MLP，多层感知机 | 网络结构 | 将输入数值映射为输出 |
| Actor，策略网络 | 网络角色 | 输出动作分布参数，决定怎样行动 |
| Critic，价值网络 | 网络角色 | 估计未来累计奖励，辅助策略训练 |
| Discriminator，判别器 | 网络角色 | 区分参考运动和生成运动，为 AMP 提供奖励依据 |
| PPO | 强化学习算法 | 利用交互经历更新策略等参数 |
| AMP | 动作引导方法 | 利用参考运动学习运动风格约束 |

训练配置：

```text
coohoi/data/cfg/train/amp_humanoid_task.yaml
coohoi/data/cfg/train/share_humanoid_task_coohoi.yaml
```

关键配置片段：

```yaml
network:
  name: amp
  separate: True
  mlp:
    units: [1024, 512]
    activation: relu
  disc:
    units: [1024, 512]
    activation: relu
```

策略主要计算路径可以理解成：

```text
观察向量 → 1024 单元隐藏层 → 512 单元隐藏层 → 动作分布参数
```

1024 和 512 是隐藏层宽度，不是机器人关节数量。`separate: True` 表示 Actor 和 Critic 使用分开的网络路径，判别器也有自己的参数。

源码入口：`coohoi/learning/amp_network_builder.py`，其中有 `eval_actor`、`eval_critic` 和 `eval_disc`。

与 YOLO 对照：

```text
YOLO：图片 → 检测网络 → 类别、检测框
CooHOI 策略：状态数值 → MLP 策略网络 → 动作
```

运行搬运策略时，负责动作决策的是 Actor。PPO 是训练算法，不是运行时另一个动作决策模型。检查点可能同时包含多个网络和统计量，不能把整个 `.pth` 等同为仅有 Actor 的裸参数。

## 8. 与前面学过的 PID、力矩和动力学怎么关联？

策略决定动作，控制器负责跟踪，动力学决定施力后的运动。

以“策略最终给出目标关节角”的架构为例：

```text
当前状态 → 策略 → 目标关节角 q_d
                         ↓
                    PD 控制器
                         ↓
                     关节力矩 τ
                         ↓
                物理仿真或真实机器人
                         ↓
                      新状态
```

一个教学用的 PD 表达式是：

$$
\tau=K_p(q_d-q)+K_d(\dot q_d-\dot q)
$$

- 策略决定希望怎么动。
- 控制器根据目标与当前状态计算控制输出。
- 动力学描述力矩、质量、惯量、接触等如何造成运动变化。

本地 `humanoid_carrybox.yaml` 的 `pdControl: True` 确认启用了 PD 路径。但是网络原始动作如何缩放、偏移、转换为具体关节目标，还需要沿任务代码继续阅读；不能把上面的教学公式直接当作该项目逐行实现。

同样，并非所有强化学习环境都输出目标关节角。有的输出速度、角度增量或力矩，要按实际接口判断。

## 10. 重要问题：怎么训练？

以下命令是项目的 Linux 使用流程说明，不是当前 CPU Windows 电脑已经可执行的操作。应在 CooHOI 项目根目录和配置好的环境中执行。

### 10.1 第一阶段：单机器人搬运训练

```bash
CUDA_VISIBLE_DEVICES=0 python coohoi/run.py \
  --task HumanoidAMPCarryObject \
  --cfg_env coohoi/data/cfg/humanoid_carrybox.yaml \
  --cfg_train coohoi/data/cfg/train/amp_humanoid_task.yaml \
  --motion_file coohoi/data/motions/coohoi_data/coohoi_data.yaml \
  --headless \
  --wandb_name "single_carry"
```

| 参数 | 含义 |
|---|---|
| `CUDA_VISIBLE_DEVICES=0` | 指定可见 GPU |
| `coohoi/run.py` | 启动入口 |
| `--task` | 选择任务 |
| `--cfg_env` | 选择环境配置 |
| `--cfg_train` | 选择训练配置 |
| `--motion_file` | 选择参考动作配置 |
| `--headless` | 不显示仿真窗口 |
| `--wandb_name` | 设置实验名称；不意味着仅设置名称就完成日志服务配置 |

本地默认配置中的一些值：

| 配置 | 值 | 含义 |
|---|---:|---|
| `numEnvs` | 4096 | 并行环境数量 |
| `episodeLength` | 600 | 回合长度设置 |
| `pdControl` | `True` | 使用 PD 控制路径 |
| `learning_rate` | `2e-5` | 学习率 |
| `max_epochs` | 50000 | 训练迭代上限 |
| `task_reward_w` | 0.5 | 任务奖励权重 |
| `disc_reward_w` | 0.5 | 判别器奖励权重 |

4096 个环境表示多份并行实验场景，不是 4096 个机器人一起搬一个箱子。降低环境数量时，需要检查采样量和训练批量的匹配关系。

这里的 epoch 不要直接套用 YOLO“遍历一次固定图片数据集”的含义。训练会持续收集新的仿真经历。

### 10.2 第二阶段：双机器人协作训练

```bash
CUDA_VISIBLE_DEVICES=0 python coohoi/run.py \
  --task ShareHumanoidCarryObject \
  --cfg_env coohoi/data/cfg/share_humanoid_carrybox.yaml \
  --cfg_train coohoi/data/cfg/train/share_humanoid_task_coohoi.yaml \
  --motion_file coohoi/data/motions/coohoi_data/coohoi_data.yaml \
  --headless \
  --is_finetune \
  --pretrain_checkpoint coohoi/data/models/SingleAgent.pth \
  --wandb \
  --wandb_name "two_agent_carry"
```

这里使用作者的单机器人权重作为示例，也可以替换为自己训练的匹配权重。

- `--is_finetune`：使用微调流程。
- `--pretrain_checkpoint`：指定作为起点的单机器人检查点。

两阶段的意义：先建立单个角色的运动与搬运能力，再学习协作。两个单独会搬运的角色放在一起，不会自动学会配合。

文档强调通过物体的运动变化获得协作反馈。可以类比两个人抬桌子时，通过桌子的倾斜感受到另一侧的动作。“隐式通信”不等于直接向对方发送一条语言指令。

## 11. 重要问题：训练完得到什么？怎样算训练好了？

核心产物是 `.pth` 模型检查点，以及用于分析的训练日志等。文档说明模型通常保存在：

```text
output/Humanoid_<日期时间>/nn/
```

策略权重表达的是根据当前观察选择动作的规则，不是一段录好的视频，也不只是一条固定关节轨迹。

```text
有 .pth 文件：说明模型被保存过
任务稳定成功：才说明具有相应任务能力
```

评价时不能只看奖励是否上升，也应重复检查：

- 是否真正完成搬运任务。
- 是否经常摔倒、掉落或卡住。
- 动作是否剧烈抖动、出现异常。
- 多次运行的成功表现是否稳定。
- 在任务允许的不同初始条件下是否仍然有效。

训练时长和最终效果取决于设备、配置与任务表现，不能保证训练到某个固定次数就一定成功。

单机器人测试示例：


## 13. 重要问题：训练结果怎样用到真实机器人？

当前文档直接支持的是在匹配的仿真任务中加载策略运行。

不能直接把人形机器人策略 `.pth` 复制到 AM970，就认为能够控制自己的机械臂。需要处理：

| 匹配内容 | 为什么需要 |
|---|---|
| 机器人结构与关节 | 人形机器人和机械臂的身体结构、自由度不同 |
| 观察来源与处理 | 真机需要传感器提供策略要求的数据，并保持顺序、单位、归一化一致 |
| 动作接口 | 需要匹配动作缩放、限位、控制方式和频率 |
| 驱动与反馈 | 网络输出要转换为真实驱动器接受的命令 |
| 物理差异 | 仿真和真实的摩擦、质量、延迟等存在差别 |

因此，“单机器人技能迁移到双机器人协作任务”和“仿真策略迁移到真实机器人”是两件不同的事。

## 16. CooHOI 完整流程：从数据输入、训练，到输出与使用

> 本节记录本次讨论的完整流程，保留讲解内容、顺序和图解。公式使用 Markdown 的 `$$` 块格式，便于预览。

好，我们把 **CooHOI 从输入数据、训练，到最后使用模型控制机器人**的完整流程连起来。

先明确：**它不是给一张图片，输出一个动作。当前这套策略主要读取仿真里的机器人和物体状态，输出关节控制动作。**

### 一、先看完整流程

```text
【训练前准备】
│
├─ 机器人模型
│  身体结构、关节、质量、运动范围等
│
├─ 仿真任务与配置
│  箱子、目标位置、物理参数、控制参数等
│
├─ 参考动作数据
│  用来提供“合理的人体动作是什么样”的示例
│
└─ 策略网络与训练算法
   Actor、Critic、AMP 判别器、PPO 更新规则
           │
           ▼
【初始化仿真环境】
生成机器人和箱子，设置初始状态
           │
           ▼
┌────────────── 训练循环 ─────────────────┐
│                                        │
│  ① 仿真状态 → 整理成观测 obs             │
│             ↓                          │
│  ② Actor 网络读取 obs → 产生动作 action  │
│             ↓                          │
│  ③ action → 目标关节角度                 │
│             ↓                          │
│  ④ PD 控制 → 关节力矩                    │
│             ↓                          │
│  ⑤ 物理仿真 → 机器人与箱子发生运动         │
│             ↓                          │
│  ⑥ 得到下一状态、任务奖励、是否结束         │
│     同时通过 AMP 得到动作模仿奖励          │
│             ↓                          │
│  ⑦ 收集一批交互数据                      │
│             ↓                          │
│  ⑧ PPO 更新 Actor 和 Critic              │
│     参考动作与生成动作用于更新 AMP 判别器   │
│             ↓                          │
│  用更新后的策略继续尝试 ──────────────────┘
│
└─ 定期保存训练参数 → checkpoint.pth
                              │
                              ▼
【推理使用】
加载训练好的 Actor 及所需归一化参数
                              │
                              ▼
当前观测 → Actor → 动作 → PD 控制 → 仿真运动
   ▲                                      │
   └────────── 下一时刻观测 ────────────────┘

此时使用训练成果，通常不再更新网络参数。
```

### 二、输入到底是什么数据？

这里要区分 **“训练系统需要的输入”**和 **“Actor 每一步收到的输入”**。

#### 1. 训练系统需要的输入

| 输入 | 用途 | 类比 |
|---|---|---|
| 机器人模型 | 确定机器人长什么样、能怎么运动 | 给学生一个身体 |
| 仿真场景与任务配置 | 定义箱子、目标和物理环境 | 设置练习场地和任务 |
| 参考动作数据 | 为动作模仿提供示例 | 展示合理动作 |
| 奖励规则 | 衡量是否完成任务、动作是否合理 | 设置评分标准 |
| 网络与训练配置 | 确定网络结构、如何更新参数 | 确定学习方法 |

**参考动作并不是每一步直接复制给机器人的指令。** 在 AMP 机制中，它主要用来帮助判别器学习什么样的动作像参考动作。

#### 2. Actor 每一步收到的输入：`obs`

`obs` 是由多个数值拼起来的向量。可以先这样理解：

```text
obs = [
    身体姿态相关信息,
    关节状态相关信息,
    身体运动速度相关信息,
    箱子相对机器人状态相关信息,
    任务目标相关信息,
    ...
]
```

这里表示信息类别；具体字段、顺序和维数，以当前任务的观测构造代码为准。

它表达的是：

> **“我现在是什么姿态、正在怎么运动、物体和目标在哪里？”**

这和 YOLO 输入图片不同：**当前策略直接获得仿真计算出来的状态信息。**

### 三、过程：从输入状态到机器人动起来

假设当前机器人正在接近箱子。

#### 第一步：策略读取状态，计算动作

```text
当前观测 obs
      ↓
Actor 神经网络
      ↓
动作 action
```

网络里的参数决定了：

> 在这种状态下，各个关节应该给出怎样的控制动作？

动作通常是一个向量：

```text
action = [a₁, a₂, a₃, …, aₙ]
```

其中各分量对应受控关节自由度的控制量。**这不是一句“搬起箱子”，而是一组能往下执行的数值。**

训练时，策略通常会按输出的动作分布采样，以进行探索；确定性演示则使用均值动作。

#### 第二步：动作转换为目标关节角度

你之前看的代码就在做这个：

```python
pd_tar = self._pd_action_offset + self._pd_action_scale * action
```

对应：

$$
q_d=b+s\odot a
$$

含义是：

- $a$：策略输出的动作向量。
- $b$：各关节的角度偏移量。
- $s$：各关节的动作缩放量。
- $q_d$：转换后的目标关节角度。
- $\odot$：对应元素相乘。

**策略的动作经过这一步，才变成各关节要到达的角度。**

#### 第三步：PD 控制根据角度误差产生力矩

可以用下面这个简化公式理解：

$$
\tau=K_p(q_d-q)+K_d(\dot q_d-\dot q)
$$

```text
目标关节角度 q_d ──┐
                   ├─ PD 控制 → 关节力矩 τ
实际角度和速度 ────┘
```

当前代码把目标角度交给仿真的关节驱动器，由驱动器结合刚度、阻尼等参数执行控制；**不是 Actor 自己在计算这个 PD 公式。**

这就关联到了你前面学的：

> **策略决定目标 → PD 追踪目标 → 力矩驱动运动。**

#### 第四步：物理仿真计算下一时刻

仿真根据力矩、质量、惯性、重力、接触和摩擦等因素，计算：

```text
机器人关节有没有转动？
身体有没有失去平衡？
手有没有碰到箱子？
箱子有没有被抬起或移动？
```

输出下一时刻的物理状态，再整理成新的 `obs`。

**这里就是你前面学的动力学发挥作用的地方。**

### 四、训练怎么让动作越来越好？

机器人动了，不代表它就完成任务。还需要评价和更新。

#### 1. 任务奖励：事情有没有做好？

任务代码根据运动结果评分，例如围绕接近物体、搬运进度等目标进行评价，具体项目由任务中的奖励函数决定。

```text
执行动作
   ↓
机器人和箱子的新状态
   ↓
任务奖励函数
   ↓
任务奖励
```

#### 2. AMP 动作模仿奖励：动作像不像参考示例？

```text
参考动作数据 ─────────────┐
                         ├─ 训练 AMP 判别器
机器人生成的动作状态 ────┘
                              │
                              ▼
                 对机器人动作给出模仿奖励
```

它关注的是动作是否具有参考动作的特征。**像参考动作，不一定就完成了搬运，所以还需要任务奖励。**

#### 3. PPO：根据一批经验更新网络

训练期间收集的数据可以概括为：

```text
当前观测
选择的动作
执行后得到的奖励
下一观测
回合是否结束
以及更新所需的概率、价值估计等
```

然后：

```text
收集一批经验
      ↓
Critic 帮助估计状态价值
      ↓
估计哪些动作比原先预期更好
      ↓
PPO 更新 Actor 和 Critic
      ↓
Actor 下次更倾向于选择带来较好结果的动作
```

**Critic 是训练时的评价辅助网络，Actor 才是直接产生控制动作的网络。**

整个过程需要不断重复。一次动作得到高奖励，并不是把这个动作直接背下来，而是通过优化修改网络参数。

### 五、训练最终输出什么？

主要输出包括：

| 输出 | 你用它做什么 |
|---|---|
| 模型检查点 `.pth` | 保存、恢复训练，或加载后推理 |
| 训练日志和曲线 | 看奖励、损失、回合表现等变化 |
| 评估结果或录制视频 | 观察训练后的动作效果，需要另外运行评估或录制 |

**`.pth` 保存的是网络参数等信息，不是一段机器人动作视频，也不是固定动作列表。**

视频中机器人每一步的动作，仍然是网络根据当时的状态实时计算的。

### 六、训练完怎么使用？

加载权重后，保留控制循环：

```text
观测 obs
   ↓
训练好的 Actor
   ↓
动作 action
   ↓
目标关节角度 q_d
   ↓
PD 控制
   ↓
关节力矩 τ
   ↓
机器人运动
   ↓
新的观测 obs
```

**推理阶段不需要靠奖励来决定当前动作，也不需要用 Critic 或 AMP 判别器来产生动作。** 演示程序仍然可能计算奖励，用来统计表现，但通常不会据此更新策略。

如果未来迁移到真实机器人，还要让真实传感器提供匹配的观测，让控制接口正确执行动作，并处理仿真与实物差异；不能直接把 `.pth` 发给电机就运行。

你前面所学与这一流程的对应关系是：

```text
传感器 / 状态估计 → 提供“现在怎么样”
策略网络         → 决定“接下来怎么动”
关节目标与 PD    → 负责“怎么追踪这个动作”
执行器与动力学   → 决定“实际上会怎样运动”
奖励与 PPO       → 负责“怎么通过练习改进策略”
```

**我们刚才跑的是“加载已有 `.pth` → 推理 → 仿真运动”；接下来你亲手训练，要走的是“反复交互 → 收集经验 → 更新参数 → 保存自己的 `.pth`”。**
