## 2. 今天先看懂第一张表的结构

**先看懂视觉基座、语言模块、动作输出头。** 看懂这三部分，再读下面的模型名称，就能知道它们在比较什么。

假设桌面有红杯子、蓝杯子和盘子，你给机器人指令：

> 把红色杯子放到盘子上。

模型需要处理三件事：

```text
摄像头画面                  语言指令
红杯子、蓝杯子、盘子       “把红色杯子放到盘子上”
        │                          │
        ▼                          ▼
   提取视觉特征                编码语言信息
        │                          │
        └────────────┬─────────────┘
                     ▼
              融合图像与任务信息
                     │
机器人自身状态 ──────┤  ← 部分模型还输入关节等状态
                     ▼
                 预测动作
                     │
                     ▼
             控制机械臂和夹爪
                     │
                     ▼
            获取新画面，继续决策
```

这张图是理解各部分职责的示意，**不是所有 VLA 都有完全相同的内部连接方式**。

对应原文表格：

| 文档中的列 | 先理解成什么 |
|---|---|
| 视觉基座 | 怎样把图片转换成可供模型使用的信息 |
| 语言／推理基座 | 怎样处理指令，并结合视觉信息 |
| 输出预测头 | 怎样把内部信息转换成机器人动作 |
| 参数量 | 模型包含多少可学习参数 |
| 语言推理能力 | 需要通过具体任务验证，不能只看“强、弱”标签 |

## 3. 视觉基座：图片不能直接当作动作使用

摄像头给出的是像素：

```text
图片
  ↓
大量像素数值
  ↓
视觉编码器
  ↓
一组视觉特征向量
```

视觉编码器通过网络计算，把像素变成更适合后续处理的表示。可以把这些表示理解为：包含物体外观、场景布局等信息的数值。

但要注意：

**视觉特征通常不是一张明确的“红杯子坐标表”，也不是一句“这里有个杯子”。** 它们是模型内部使用的向量。

这和前面学过的 YOLO 有联系：

```text
YOLO：
图片 → 特征提取 → 检测头 → 框和类别

VLA 的一种结构：
图片 → 视觉特征 → 与语言信息融合 → 动作输出
```

所以，VLA 可以使用视觉编码器直接处理图片，**并不一定先运行 YOLO，再把检测框交给策略**。

表里的 `SigLIP`、`DINOv2`、`ViT` 等，先把它们看成不同的视觉模型或结构名称，不用第一天就记住全部内部细节。它们属于不同层次的名称，后面的 ViT 问答会具体区分。

## 4. 语言模块：同一张图片，指令不同，动作应该不同

桌面没有变化，但指令可以变化：

```text
同一张桌面图片
      │
      ├─ “拿红杯子” → 机械臂应接近红杯子
      │
      ├─ “拿蓝杯子” → 机械臂应接近蓝杯子
      │
      └─ “把盘子移到左边” → 操作对象变成盘子
```

语言提供的是**任务条件**。

因此模型不能只知道画面里有什么，还要把指令中的对象、位置和操作与画面对应起来：

```text
“红色杯子” ──对应──→ 画面中的目标物体
“盘子上”   ──对应──→ 目标区域
“放到”     ──对应──→ 希望完成的操作
```

这仍然是网络中的数值计算，不要求程序先生成一份中文分析，再执行动作。

**能够接收语言指令，也不等于一定能自由聊天、进行可靠的复杂推理。**

例如，原文把 Octo 写成“不支持语言对话”，不能由此推断它“不接受语言任务”。官方说明它支持自然语言指令和目标图像作为任务条件。[Octo 官方说明](https://octo-models.github.io/)

## 5. 动作输出头：最终要给机器人什么？

前面已经理解：

```text
CooHOI Actor → action → 控制目标 → PD → 机器人运动
```

VLA 也必须把内部表示转换成可执行动作。

动作形式可能是：

```text
形式 A：关节目标
[q₁, q₂, …, 夹爪目标]

形式 B：末端运动增量
[Δx, Δy, Δz, 旋转增量…, 夹爪控制]

形式 C：未来一段动作
[aₜ, aₜ₊₁, aₜ₊₂, …]
```

这些是不同接口的示例，**具体项目输出哪一种，要看代码和数据定义**。其中“一段动作”描述的是时间范围，它里面的每一步仍然可以使用关节目标或末端增量等表示方式。

文档“输出预测头”这一列，主要在比较动作如何产生、如何表示：

| 表格中的写法 | 当前先理解到什么程度 |
|---|---|
| 离散 Action Token | 把动作数值转换成离散编号，预测编号后再解码成动作 |
| 连续动作输出 | 输出连续控制量 |
| 扩散动作头 | 通过逐步去噪生成动作或动作序列 |
| 流匹配动作头 | 学习从噪声到动作的连续变换过程 |

扩散和流匹配后面再展开，包括要求补充的 Diffusion Policy。今天先知道：**它们是在讨论“怎样生成动作”，不是不同的电机接口。**

## 6. 横着读表里的一行：OpenVLA

原始 OpenVLA 可以画成：

```text
摄像头图片
    │
    ▼
SigLIP + DINOv2
提取视觉特征
    │
    ▼
投影模块
把视觉特征映射到语言模型可接收的表示空间
    │
    │          语言指令
    │             │
    └──────┬──────┘
           ▼
       Llama 2
结合图像信息与指令，预测动作 token
           │
           ▼
       动作解码
把 token 转换为连续动作数值
           │
           ▼
      机器人控制接口
```

这就是官方描述的视觉编码器、投影模块和语言模型三部分，以及动作解码流程。[OpenVLA 官方架构说明](https://openvla.github.io/)

现在就能把表格中的三个名字连起来：

> **视觉模型提供图像表示，语言模型结合指令处理这些信息，输出动作表示，再解码成机器人动作。**

原文中的一个关键点需要纠正：原始 OpenVLA 的动作 token 训练使用**交叉熵损失**，表格写的“离散化 Action Token（L1 损失预测）”混淆了不同训练设计。后面读具体版本时要分开看。[OpenVLA 原论文](https://openreview.net/attachment?id=ZMnD6QZAE6&name=pdf)

## 8. 重点问题：为什么 OpenVLA 官方架构里面视觉写的是 ViT？

学习时提出的问题：

> OpenVLA 官方架构里面视觉怎么说的是 ViT 呢？

**不矛盾：ViT 是网络结构的名称，DINOv2、SigLIP 是这里采用的具体预训练视觉模型。OpenVLA 使用的这两个视觉分支，都基于 ViT。** 前面的讲解需要补上这一层关系。

官方图写的是结构层面的 **ViT**，正文则进一步说明，视觉编码器由 **DINOv2 和 SigLIP** 两个分支组成。[官方架构图](https://openvla.github.io/static/images/openvla_model.jpg)、[官方文字说明](https://openvla.github.io/)

可以这样理解：

```text
同一张摄像头图片
          │
          ├──────────────────┐
          ▼                  ▼
     DINOv2 分支         SigLIP 视觉分支
     基于 ViT            基于 ViT
          │                  │
          ▼                  ▼
       视觉特征 A         视觉特征 B
          │                  │
          └────────┬─────────┘
                   ▼
                特征拼接
                   ▼
              Projector 投影模块
                   ▼
              送入语言模型
```

**它们不是“ViT → DINOv2 → SigLIP”三个模块依次连接，而是两个 ViT 视觉分支分别处理图片，再融合特征。**

ViT 全称是 **Vision Transformer，视觉 Transformer**。它处理图片的基本思路是：

```text
图片
 ↓
切成许多小块 patch
 ↓
每个小块转换成向量，并加入位置信息
 ↓
Transformer 处理小块之间的关系
 ↓
输出视觉特征
```

所以这几个名字分别回答不同的问题：

| 名称 | 回答什么问题 |
|---|---|
| **视觉编码器** | 这个模块负责什么？——提取图片特征 |
| **ViT** | 采用什么网络结构？——视觉 Transformer |
| **DINOv2、SigLIP** | 使用什么预训练模型？——这里的两个视觉分支 |
| **Projector** | 特征怎样接到语言模型？——映射到匹配的表示空间 |

与之前理解的 MLP 类似：

> **Actor 是职责，MLP 是结构；视觉编码器也是职责，ViT 是它可以采用的结构。**

这里讨论的是 OpenVLA 实际采用的视觉分支；不要把 SigLIP 的整个图文预训练系统，与其中用于 OpenVLA 的视觉编码器混为一谈。

## 10. Projector：视觉特征为什么还要投影才能送进语言模型？

上次已经弄清楚：

```text
视觉编码器：模块职责
ViT：网络结构
DINOv2、SigLIP：OpenVLA 采用的两个预训练视觉分支
```

**现在把它们往后接一步：视觉特征为什么还要经过 Projector，才能送进语言模型？**

在 OpenVLA 官方图中看到的链路是：

```text
图片
 ↓
DINOv2 + SigLIP
 ↓
拼接视觉特征
 ↓
Projector（投影模块）     ← 今天先看这里
 ↓
语言模型
 ↓
动作 token
```

### 10.1 视觉网络和语言模型处理的“向量格式”不一定相同

图片经过视觉编码器后，变成一组特征向量：

```text
图片中的多个 patch
        ↓
[视觉向量₁，视觉向量₂，视觉向量₃，……]
```

语言指令也会变成向量：

```text
“把红杯子放到盘子上”
        ↓
分词，得到文本 token
        ↓
[文本向量₁，文本向量₂，文本向量₃，……]
```

它们都是数字，但**维度和学到的表示方式不一定一致**，不能因为都是向量，就直接拼起来使用。

### 10.2 Projector 把视觉特征转换成语言模型可接收的表示

```text
拼接后的视觉向量
       │
       ▼
可学习的投影网络
       │
       ▼
与语言模型输入维度匹配的视觉向量
```

举一个纯粹用于理解的例子，数字不是 OpenVLA 的实际配置：

```text
视觉侧输出：每个向量 100 个数
语言侧要求：每个输入向量 200 个数
                   ↓
Projector 学习一个映射
                   ↓
把 100 维特征转换成 200 维表示
```

**它不是简单补 100 个零，也不是把图片先翻译成一句中文。** 它通过网络计算产生新的表示，参数可以通过训练学习。

维度匹配解决的是“能接进去”；训练则帮助它学到“怎样转换才对后面的任务有用”。

### 10.3 图像信息和指令，在语言模型里共同参与动作预测

```text
图片 → 视觉编码器 → Projector → 视觉表示 ──┐
                                          ├─→ 语言模型 → 动作 token
指令 → 文本分词与嵌入 → 文本表示 ─────────┘
```

例如同一张图片里有红、蓝两个杯子：

```text
图像提供：场景里有哪些视觉信息
指令提供：这次要求操作哪个对象、完成什么任务
                     ↓
模型结合两者，预测动作
```

这不是说程序内部必然明确列出“红杯子坐标”“蓝杯子坐标”，而是相关信息通过向量和网络计算共同影响输出。

### 10.4 和前面学的 Actor 怎么对应？

```text
CooHOI：
已经整理好的状态向量 → MLP Actor → 动作

OpenVLA：
图片、文字
    ↓
各自编码并对齐表示
    ↓
模型联合处理
    ↓
动作 token → 解码成动作
```

CooHOI 的输入已经是适合网络处理的状态数值；OpenVLA 需要先把图片、文字处理成合适的表示。

**所以 Projector 的作用就是：连接视觉编码器和语言模型，让视觉信息能够进入后续动作决策。** 接下来再看最末端的“动作 token”，整条输入—模型—动作链路就能接起来了。

## 11. 动作 token：模型输出的编号怎样变成机械臂动作？

我们接着 Projector 往后看：**语言模型输出的“动作 token”，究竟怎样变成机械臂动作？**

今天讲的是**原始 OpenVLA 的离散动作方案**，先不混入 OFT、扩散和流匹配。

### 11.1 先看完整链路

```text
图像 → 视觉编码器 → Projector ──┐
                                ├─→ 语言模型
指令 → 文本 token → 文本向量 ──┘        │
                                       ▼
                                预测动作 token
                                       │
                                       ▼
                                 解码、反归一化
                                       │
                                       ▼
                                动作数值 → 控制器
```

**动作 token 是代表动作数值的离散编号。它不是电机 ID，也不是“抓取”“抬起”这样的完整动作名称。** 原始 OpenVLA 的实现会把连续动作离散化，并映射到语言模型词表中的 token。[官方动作编码实现](https://github.com/openvla/openvla/blob/main/prismatic/vla/action_tokenizer.py)

### 11.2 为什么把动作变成编号？

你已经知道机械臂的动作可以是一组连续数值，例如下面这个**假设的控制接口**：

```text
动作 = [Δx, Δy, Δz, 旋转增量…, 夹爪控制]
```

但语言模型原本擅长的是预测 token：

```text
已有输入 → 预测下一个 token
```

于是可以给动作建立一套编号规则：

```text
连续动作数值
     ↓
划分数值区间
     ↓
用编号代表所在区间
     ↓
把编号映射成 token
```

这样，动作预测就能使用语言模型的 token 输出机制。

### 11.3 用一个简化例子：把“沿 X 移动”分成几个档位

以下是教学用的玩具例子，**不是 OpenVLA 的真实分箱数、单位或编号**。

假设某个控制接口允许每步沿 X 移动 −5～+5 厘米，我们用五档近似表示：

| 示意 token | 解码后的代表值 |
|---|---:|
| A | −4 厘米 |
| B | −2 厘米 |
| C | 0 厘米 |
| D | +2 厘米 |
| E | +4 厘米 |

训练数据里有一次示范：

```text
当时画面：机械臂位于杯子旁边
指令：拿起杯子
示范动作：沿 X 移动 +2.3 厘米
```

编码时：

```text
+2.3 厘米
    ↓
落入 D 对应的区间
    ↓
用 token D 作为这一维的训练目标
```

推理时：

```text
模型看到类似画面和指令
          ↓
预测 token D
          ↓
查映射规则
          ↓
得到 +2 厘米
          ↓
交给控制接口执行
```

你会发现：**原来的 +2.3 被近似成了 +2。这就是离散化带来的精度损失。**

分得更细，可以降低这种量化误差，但模型仍然需要预测正确的档位。

### 11.4 一组动作，通常需要多个动作 token

接着上面的假设接口：

```text
位置变化       姿态变化       夹爪控制
Δx Δy Δz       三个旋转分量    g
 │  │  │         │ │ │        │
 ▼  ▼  ▼         ▼ ▼ ▼        ▼
T₁ T₂ T₃         T₄ T₅ T₆     T₇
```

**这些 token 可以共同表示“同一个控制时刻的一组动作”，不一定表示七个时间步。**

这是个重要区别：

```text
同一时刻的不同动作分量：
[向哪移动，怎样旋转，夹爪如何开合]

不同时间的一段动作：
[这一时刻的动作，下一时刻的动作，再下一时刻的动作]
```

动作有多少维、各维是什么意思，由具体数据和控制接口规定。不能看到七个输出，就认定它们是七个关节角。

### 11.5 OpenVLA 实际还要做“归一化”和“反归一化”

不同动作分量的范围不一样，所以不能把模型输出的数直接当作米或弧度使用。

原始 OpenVLA 的解码实现，先把 token 还原为归一化动作，再根据选定数据集的动作统计量进行反归一化。[官方 predict_action() 实现](https://github.com/openvla/openvla/blob/main/prismatic/extern/hf/modeling_prismatic.py)

可以这样记：

```text
训练数据准备：
原动作 → 归一化 → 离散编码 → 动作 token 标签

推理输出处理：
预测动作 token → 解码 → 反归一化 → 动作数值
```

因此，**模型权重、动作编码规则、归一化统计量和机器人控制接口，必须对应起来。** 解码出来的数字有了正确含义，才能交给控制器。

### 11.6 训练时和推理时，动作 token 各在哪里？

```text
训练时：

图像＋指令 → 模型 → 预测 token 的分布
                          │
示范动作 → 编码成目标 token ┘
                          ↓
                       计算损失
                          ↓
                       更新参数
```

```text
推理时：

新图像＋指令 → 模型 → 生成动作 token
                           ↓
                         解码
                           ↓
                      执行机器人动作
                           ↓
                    获取新图像继续决策
```

**训练时有示范动作作为学习目标；推理时没有示范答案，要靠训练后的模型自己预测。**

现在，把已经学过的三个部分串起来：

```text
视觉编码器：图片 → 视觉特征

Projector：视觉特征 → 语言模型能接收的表示

动作解码器：模型生成的动作 token → 控制接口需要的动作数值
```

**Projector 解决“图像信息怎么进模型”，动作编码与解码解决“动作怎么成为模型可学习、可输出的表示”。**
