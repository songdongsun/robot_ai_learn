# DiT4DiT 与 VLA 的关系及工作原理学习记录

记录日期：2026-11-26。

学习位置：`06-策略抓取或抓取VLA/大模型控制、VLA、VLM/05DiT4DiT-LIBERO/01DiT4DiT-LIBERO训练与评估.md`。

前置学习：已学完上一节 MuJoCo 中 ACT、π0、SmolVLA 的采集、训练与部署内容。本文记录已讨论的概念，不代表 DiT4DiT 实操已经完成。

## 1. 我的疑问：这些与前面的 VLA 是并列的吗？是模型还是框架？

**VLA 是一类模型的称呼；π0、SmolVLA、DiT4DiT 是具体策略方案，可以从机器人控制效果、结构和训练方式等角度比较。**

VLA 是 Vision-Language-Action，描述利用视觉和语言条件生成动作的模型形式。模型还可以接收机器人本体状态。

可以类比视觉领域：YOLO 是具体目标检测模型，“目标检测”是任务类别，两者不是并列层级。同样，π0 是具体 VLA 模型，不是与 VLA 并列的另一种模型。

| 名称 | 在本章中的角色 |
| --- | --- |
| VLA | 视觉—语言—动作模型的一类形式 |
| ACT | 具体机器人策略方法，基本形式不要求语言输入，不能把所有 ACT 都称为 VLA |
| π0、SmolVLA | 具体 VLA 模型方案 |
| DiT4DiT | 结合视频与动作生成的具体策略模型／方法 |
| LeRobot | 提供数据处理、策略实现、训练等功能的软件框架 |
| LIBERO | 机器人操作任务、数据与评测基准 |
| MuJoCo | 底层物理仿真引擎 |

DiT4DiT 官方强调 Video-Action Model，也使用语言目标。视频—动作模型与 VLA 不必理解成互斥类别；前者强调视频动态建模，后者强调视觉、语言到动作的关系。

## 2. 为什么同一个东西有时叫模型，有时叫框架？

- **模型**：具体网络结构、参数以及输入到输出的计算。
- **方法框架**：多个网络模块的组合方式及训练方法。
- **工程实现**：数据读取、训练脚本、推理服务、评估脚本等代码。

因此，说“DiT4DiT 模型”是在说它如何预测动作；说“DiT4DiT 方法框架”可能是在说视频分支、动作分支和训练目标的整体设计。这里的“方法框架”与 LeRobot 这样的软件框架不是同一层含义。

## 4. 先明确模型输入、输出

以“把杯子放到盘子上”为例：

| 符号 | 含义 |
| --- | --- |
| $o_t$ | 当前视觉观测，例如主视角和腕部视角图像 |
| $s_t$ | 当前机器人状态，具体字段由数据和模型约定 |
| $\ell$ | 语言任务指令 |
| $a_t$ | 一个控制时刻的动作 |
| $H$ | 一次预测的动作数量 |
| $A_t$ | 未来动作块 |

$$
A_t=[a_t,a_{t+1},\ldots,a_{t+H-1}]
$$

例如预测 16 个动作，每个动作 7 维，则动作数组形状为 $16\times7$。这是帮助理解的示例，不是已核实的 DiT4DiT 默认 horizon。

动作可能表示位置增量、旋转调整与夹爪控制，也可能使用其他定义。**不能仅凭“7 维”认定它是关节角或者米制位移**；必须核对控制器、坐标系、归一化与数据字段。

模型输出的是控制量，不是“抓住杯子、抬起来、放下”这样的文字步骤。

## 5. 为什么用视频模型？

识别“杯子在哪里”，与掌握“夹爪接近、接触、抓起杯子时画面如何变化”，需要的信息不完全相同。

视频生成／预测任务促使模型学习时序与运动规律。DiT4DiT 利用这类模型的中间表示，为动作生成提供条件。

**这不代表视频模型已经准确掌握物理定律，也不保证它预测的未来正确。** 这里利用的是从数据学习到的动态先验。

与 π0 的学习联系起来：视觉语言模型的表示可以帮助动作生成，视频生成模型学到的动态表示也可以作为动作生成的条件。

## 6. 两个 DiT 分别做什么？

DiT4DiT 的核心是串联的 **Video DiT 与 Action DiT**：

```text
当前视觉观测 + 语言目标
          ↓
       Video DiT
          ↓
    提取中间视觉特征
          ↓
       Action DiT ← 机器人状态 + 带噪动作序列
          ↓
    通过 flow matching 生成动作块
```

视频分支以 Cosmos-Predict2.5-2B 初始化；动作分支利用视频特征、机器人状态及带噪动作进行生成。

**教材中把一个 DiT 解释为扩散、另一个解释为整体框架的说法不够准确。** 应以官方双 DiT 架构为准。

## 7. 是否必须先生成完整视频，再让机器人照着做？

**不必。关键传递的是视频模型的中间特征，而不一定是可直接观看的完整视频。**

类比视觉算法：

```python
features = backbone(image)
prediction = head(features)
```

检测头使用 backbone 的特征，不需要先得到 backbone 原任务的最终分类结果。类似地，DiT4DiT 从视频分支指定层、指定 flow 时间步提取中间激活，供动作分支使用，无需完整重建视频。

概念上写成：

$$
(o_t,\ell)\longrightarrow F_t
$$

$$
(F_t,s_t,\text{动作噪声})\longrightarrow A_t
$$

这里只是概念简写，省略了视频潜变量、flow 时间步等内部输入，不能当作完整函数签名。

## 8. 动作生成迭代与机器人执行时间不同

动作生成可以从随机动作数组开始，由模型预测向量场，迭代得到最终动作块。**生成过程中的向量场不等于机械臂实际运动速度。**

| 概念 | 含义 |
| --- | --- |
| 动作块里的时间顺序 | 机器人未来依次执行的控制时刻 |
| flow 生成迭代 | 模型内部把噪声变成动作的计算步骤 |

例如，生成迭代 10 次后得到 16 个动作，这两个数字不必相同。中间的带噪动作不会每更新一次就发送给机器人执行。

这只是先区分两种基本时间概念；论文的 tri-timestep 机制还需要单独学习，不能直接等同于“真实控制时间、视频时间、动作时间”三个泛称。

## 9. 如何在 LIBERO 中执行？

下面是概念伪代码，不是仓库真实 API：

```python
obs = env.reset()
done = False
while not done:
    action_chunk = policy.predict(
        images=obs["images"],
        state=obs["state"],
        instruction=task_instruction,
    )
    for action in action_chunk[:execute_steps]:
        obs, reward, done, info = env.step(action)
        if done:
            break
```

一次预测多少个动作，与一次实际执行多少个动作，未必相同。执行部分动作后重新观察，可以根据最新状态重新预测。

教程采用两个进程：

- **policy server**：加载模型、接收条件、预测动作。
- **LIBERO client**：提供观测、执行动作、判断任务是否成功。

两个进程可以位于同一台服务器，不意味着一定要两台电脑。

## 10. 教程实操目标与当前学习边界

教程记录的 10 个任务各测试一次、成功 10 次，是链路检查结果，不能当作充分评测的性能结论。

两步训练验证数据读取、前向传播、反向传播和优化器更新可用，不代表模型已经训练好。本章 smoke test 冻结 backbone，主要验证动作分支训练，不能与论文完整联合训练混为一谈。

教程部分命令引用作者服务器上的 `env.sh` 和封装脚本，实操前需要确认文件是否提供、路径是否适用，不能直接照抄服务器绝对路径。

当前已讨论模型层级和基本信息流。后续继续学习：
